NOC Agent upgrade operations
============================

Local checks
------------
scripts\check_all.bat
scripts\check_all.bat -IncludeBrowser
scripts\check_browser.ps1
scripts\smoke_upgrade.ps1

The main checks run without production dotenv, provider credentials or a live
NOC node. PostgreSQL integration requires APPROVAL_TEST_POSTGRES_URL pointing to
localhost/noc_agent_approval_test; tests use isolated UUID schemas. Actual
sandbox tests require SANDBOX_TEST_IMAGE set to a pre-pulled reviewed digest.
Reports/logs are written under .check-results (ignored by Git).

Development stack
-----------------
docker compose --env-file .env.example up --build --detach
Open http://localhost:8080. The root Compose file defaults to DATA_MODE=fixture,
an external worker and a dedicated PostgreSQL control database. The mock UI
does not represent live network state. Ports bind to localhost. The old
backend/docker-compose.yml is retained for compatibility; prefer root compose.yml.

Production prerequisites
------------------------
Provide a private runtime env file and run Compose with an explicit --env-file.
Set DEPLOYMENT_MODE=production, DATA_MODE=live, WORKER_MODE=external,
AUTH_MODE=bearer, explicit CORS origins and a PostgreSQL+asyncpg DATABASE_URL.
The root Compose DSN uses CONTROL_DATABASE_*; set a private non-demo password.
Set NOC_RUNTIME_ENV_FILE to the private runtime file. Configure inventory/alarm
DSNs independently; they are not the control database. Terminate HTTPS at the
organization ingress. No production deployment is performed by the check scripts.

Generate opaque credentials locally with backend/scripts/create_principal.py.
Store raw tokens privately, configure only principal digests/roles/scopes, and
rotate by replacing the configured digest. Local mode is development-only.
Subjects own conversations; admin can inspect all owners. A scoped principal
can use SSH only on its host/service scope. Alarm/inventory aggregate tools are
denied for restricted host scopes until a row-scoped data adapter is provided;
hosts=["*"] explicitly grants aggregate-data access. Header-supplied identities
and requested_by fields are never authorization sources. This is a bearer auth
layer, not an organization SSO/JWKS integration.

SSH/remediation
---------------
Verify fingerprints independently, mount known_hosts/key files read-only and
configure SSH_KNOWN_HOSTS/SSH_KEY_PATH to container paths. Do not enable auto-add
in production. Set exact SSH_ALLOWED_HOSTS and SSH_ALLOWED_SERVICES.
ALLOW_DOCKER_RESTART is a separate opt-in. No allowlist means no remediation.
Per-host guards serialize approvals across conversations and impose cooldown.
Known exit status and post-check recovery are distinct. Closing SSH cannot
retract a command that reached the node. Timeout, disconnect, lost worker or
lost persistence may require reconciliation; do not retry the command manually
until the remote outcome has been checked.

Unknown execution
-----------------
Wait for the possible native dispatch window to close, inspect the node/service
and record evidence. Reconciliation inside that window returns a retry delay.
An admin can use the Run status
panel to reconcile an unknown run. The backend records the observation and
releases the run without rerunning or resuming its command. Cooldown still
applies. For a legacy approval without a run, an admin can inspect
GET /api/operations/approvals/{conversation_id}/{call_id} and record verified
evidence with POST to the same path plus /reconcile. Do not edit status merely
to enable retry. A dispatch deadline does not prove the remote command stopped;
the operator must verify the remote outcome and any still-running process.

Database release and legacy adoption
-----------------------------------
Stop writers before cutover. Take and verify a separate backup before adopting
the legacy three-table schema. Do not run against the only copy of production.

python backend/scripts/control_database.py backup-sqlite --source OLD.db --backup BACKUP.db
python backend/scripts/control_database.py adopt-sqlite --source OLD.db --backup BACKUP.db --maintenance

Production startup checks the Alembic revision; migrations run once as the
Compose migrate service/release job. Development startup upgrades only a fresh
or already versioned DB. Unversioned legacy DBs require explicit adoption.

To copy the original three-table SQLite schema into an EMPTY PostgreSQL control
database, set the destination DATABASE_URL and run:
python backend/scripts/control_database.py cutover-postgres --source OLD.db --backup BACKUP.db --owner SUBJECT --maintenance

The tool rejects nonempty destinations and sources containing run history;
it does not silently discard new tables or merge two writers. IDs are preserved,
pending approvals expire, uncertain approvals remain blocked, and sequences are
reset. Review owner assignment and counts before switching DSNs. Keep the old
backup unchanged. After new writes on PostgreSQL, rollback requires reconciling
those writes; changing the DSN back is not a valid rollback by itself.

PostgreSQL backup/restore
------------------------
Use pg_dump --format=custom and pg_restore into a separate empty database.
Compare conversation/message/run/event/audit counts, sample Unicode history,
foreign keys, and readiness. smoke_upgrade.ps1 performs this rehearsal only on
its generated fixture project and removes its own containers/volume afterward.
Production backup retention, encryption, storage and restore schedules belong
to the deployment environment and are not configured by this repository.

Workers, outages and cancellation
--------------------------------
Run python -m worker from backend. Workers claim jobs conditionally, heartbeat
leases and fence stale owners before new dispatch and event/checkpoint commits.
Expired running work is conservatively failed or marked unknown; it is never
automatically retried as a write. Read retries can be initiated as a new run.
The 30-second shutdown drain precedes cancellation; keep container stop grace
above that. Database outages can leave a durable claim; recover/reconcile after
the database returns. The runtime uses versioned JSON checkpoints in the control
database, not LangGraph/PostgreSQLSaver. A changed built-in/catalog or unsupported
checkpoint version blocks resumption. Explicit checkpoint migration remains an
architecture task before broader workflow upgrades.

Stop calls the cancel API. Switching conversations, closing a tab or reconnecting
only detaches the stream. Operator interventions are accepted at approval
checkpoints and apply after the current tool batch; they cannot alter the saved
approval action. Rejected calls produce tool results and the remaining batch
continues. Admission limits bound active runs per actor.

Custom skill operations
-----------------------
The full package/AST/domain/run-spec workflow is documented in
operations/skill-packages.txt. Create an Agent Skill starter locally:
python backend/scripts/create_skill.py .check-results/my-alarm-skill --name alarm-summary
python backend/scripts/package_skill.py .check-results/my-alarm-skill .check-results/my-alarm-skill.zip

Package the included example:
python backend/scripts/package_skill.py skill_examples/custom_alarm_summary .check-results/custom_alarm_summary.zip

Use Skills to inspect a ZIP before uploading. Both legacy manifest.json packages
and SKILL.md Agent Skill packages are supported. Run validation offline, or
explicitly opt into the selected LLM provider for domain/run-spec suggestions.
The report records file/line AST findings, taxonomy, LLM status, effective schemas,
per-script hashes and smoke results. All bundled entrypoint scripts must pass.
A different skill reviewer must inspect source/manifest/report and submit review
notes; approval repeats sandbox tests. Admin activation selects
an immutable name/version/hash. New runs select the active version, waiting
runs retain their pins, and revoke blocks subsequent execution of that version.
The resolved run-spec is hashed separately from the uploaded archive. Review
must include the current report_hash; concurrent re-analysis/revoke invalidates
stale review requests. Apply release migration 0009 before starting production.
Old archive bytes are preserved. Previously approved versions without a current
report cannot be newly activated; upload/review a new version under this policy.
Custom skills currently support bounded scalar input fields and read-only
transformations of supplied data. They do not receive database/SSH credentials,
network access, arbitrary package installation or connector capabilities.

Configure SANDBOX_IMAGE as a pre-pulled immutable Python image digest. Docker CLI
is included in the runtime image. Use a dedicated sandbox daemon via authenticated
TLS (DOCKER_HOST/DOCKER_TLS_VERIFY/DOCKER_CERT_PATH), with certificate mounts readable
by UID 65532. Do not point this at a business/container orchestration daemon.
No host Docker socket is required. Artifact transfer uses a UUID-named volume;
the transfer container is never started, the execution volume is read-only, and
both containers/volume are removed after the run. If the daemon becomes unavailable
during cleanup, inspect only resources labeled noc.skill.sandbox=true, verify
ownership/age before removal and investigate the broker outage. Never daemon-prune.
Static scanning is a review aid; sandbox isolation is still required.

Monitoring and release limits
-----------------------------
/health is liveness. /ready checks startup/drain, the control DB and embedded
worker when applicable. /api/operations/metrics is admin-only and reports bounded
status aggregates, queue age, expired leases and approval backlog. Request IDs
are returned in X-Request-ID and included with run IDs in audit/telemetry context.
Langfuse enqueue/update failures do not stop execution; network flush is moved
off the per-turn critical path. Audit remains in the control database.

The endpoint reports a bounded sample rather than fleet-wide billing statistics.
The metrics endpoint samples the latest 1000 completed steps for mean/p95 latency
and reported token usage; missing usage is marked incomplete. Run admission also
enforces a configured token estimate. Optional LLM_RUN_COST_LIMIT requires an
LLM_MODEL_PRICES_JSON entry for every candidate model, in LLM_BUDGET_CURRENCY,
with a managed LLM_PRICE_CONFIG_VERSION. Estimates include configured retry and
fallback bounds and survive approval checkpoints; unknown historical cost cannot
be reset to zero when enabling a cost cap. These estimates are not billing data
or a replacement for provider-side spending limits. No prices are hard-coded.

Remaining environment-level work includes production latency certification,
fleet topology correlation, organization SSO, automatic retention scheduling,
holdout quality certification or a staging SLA. Configure those with the target
environment and measured data; do not infer readiness from fixture pass counts.

Retention preview: python backend/scripts/retention.py --days 30
Apply only the reviewed policy by adding --apply. It deletes old terminal-run
events/checkpoints while preserving messages, audit, idempotency records and
uncertain work. Expired event cursors require a snapshot reload. Scheduling and
backup retention are environment decisions; this job is not auto-enabled.

Optional paid quality evaluation is a separate workflow_dispatch job. It requires
the authorize_paid_calls checkbox and an explicitly configured online-evaluation
environment/provider. Set provider-side spending limits before invoking it.
Offline pull-request checks do not use this job or need API keys.

Independent data sources (P1-06)
--------------------------------
Alarm (ClickHouse) and inventory (PostgreSQL) connectors now connect lazily on
first use (services/connectors.py). Startup and the worker no longer wait for
them, so one source being down does not stop the other, the SSH remediation
tool, or the application. The control database remains a hard dependency.
Behaviour: connect deadline 8 s; after a connection failure the source is
refused for 1 s, doubling to a 30 s cap, then retried; a query error (bad SQL)
does not mark the source down; a lost connection drops the client and reconnects.
A failed source yields SYSTEM_ERROR with error_code CONNECTOR_UNAVAILABLE and
"no substitute data was used". device_inventory_lookup still returns inventory
with alarm_source "unavailable" and active_alarms null (unknown, not zero).
Alarm statistics and enrichment need both sources and fail with the named one.
States: not_configured (host unset), unknown (never measured), healthy,
unavailable, each with checked_at and only the exception TYPE as error_code
(messages can hold hosts/credentials). GET /ready returns 200 with
status "degraded" and a sources block when a source is down (readiness is gated
by the control database only, so a data outage does not restart pods);
GET /api/operations/connectors (viewer/operator/approver) returns the same
measured state. Probes are cached 30 s. No demo or fixture data replaces a
failed live source; fixture data_mode is an explicit separate setting.

Evidence and answer grounding (P2-02)
-------------------------------------
Tool evidence now carries observed_at, observed_basis, oldest_event_at, freshness,
clock_skew_suspected, record_count and field names (services/evidence.py).
- observed_at is the NEWEST RECORD EVENT TIME (time_created/observed_at/timestamp/
  event_time; naive times are read as UTC). It is never the retrieval time and it
  does not prove the source is current: a quiet network has old alarms and an
  outage also has none. Hence freshness stays "unknown" unless a result carries an
  explicit as_of (source snapshot time): then fresh/stale is judged against
  EVIDENCE_STALE_SECONDS (default 900). Times more than 2 minutes in the future set
  clock_skew_suspected and never count as fresh. No time at all => observed_at null.
- evidence_id is a hash of the payload, so identical data gives the same id.
Final answers are checked deterministically (services/grounding.py) against THIS
run's tool messages: cited ev_ ids must have been returned by a successful tool
call; the answer must cite when evidence exists; numbers with two or more digits
(or a decimal part) must appear in tool results or the user's request.
Statuses: grounded, not_applicable, uncited, invalid_citation, unsupported_numbers.
EVIDENCE_ENFORCEMENT=off|warn|strict (default warn): warn adds "grounding" to the
final_answer event; strict ends the run with error ANSWER_UNGROUNDED and no final
answer. strict is opt-in: a number the model derived itself (a sum, a ratio) is
reported as unsupported, which is intended. This catches fabricated references and
invented figures; it cannot judge reasoning quality, so it is not a groundedness
certification. That still needs a labelled holdout reviewed by NOC staff.

Adversarial evals (P2-06)
-------------------------
python -m evals.adversarial (also a CI step and part of scripts/run_eval_suite.ps1)
runs 16 fixed, labelled attacks from backend/evals/cases/adversarial_cases.json
against the REAL engine, executor, policy, validators and skills with scripted
"naive" models that obey the attack. Each case scores the trace AND counted side
effects (SSH commands dispatched, database queries, sandbox runs, approvals),
never only the model's text. Categories: tool-output injection, skill-reference
injection, cross-site read (by id, by name, aggregate tool, brokered script),
schema explosion (deep/wide/NaN/extra field), secret leakage, truncated or
filtered output with a tool call, bypass of the load-instructions gate and a
fabricated-evidence answer. Offline: no network, no credentials, no model, no
upload; the dataset is versioned with the code. tests/test_adversarial.py also
runs mutation checks: removing approval gating, site authorization, redaction,
the instruction gate or schema validation must turn the matching case red.
Writing this suite found a real gap, now fixed: output redaction did not mask
unlabelled credentials such as sk-... API keys, AWS access key ids, GitHub and
Slack tokens, JWTs or "my password is X". Not covered here (needs opt-in budget
and a model): generated red-team prompts against a live model, SSE lag/p95
latency, dependency fault injection and rollback rehearsal. Those stay separate
release gates. Approval replay and worker fencing are covered by their own tests.

Schema integrity and hygiene (P2-07)
------------------------------------
Migration 0012 adds CHECK constraints on status for runs, run_jobs,
tool_executions, run_steps, pending_approvals and skill_versions. The allowed
values live in repositories/status_values.py (union of everything the code writes
or reads; adding a status means editing that file, shipping a migration that
replaces the constraint, and changing the code together). Before touching any
table the migration audits existing rows and ABORTS with the table, value and row
count of every unexpected status; nothing is rewritten silently. Resolve those rows
(reconcile or correct them) and rerun. Back up first; downgrade needs backup/restore.
Verified on SQLite (fresh, legacy-abort, keys/indexes/data preserved) and PostgreSQL
16 (migration rehearsal and run tests). A test also scans services/controllers for
status literals so a new status cannot be written without updating the constraint.
Ruff now also enforces F401/F811/F841 (unused code), B023 and ASYNC; 33 unused
imports were removed. Rules are widened gradually, not all at once.
backend/noc_agent.dump is a tracked PostgreSQL custom-format dump (141 KB, added in
commit 82fde3a). Nothing in the repository references it. Its contents were NOT read
here, so it is unknown whether it holds secrets or production data. Decide whether to
delete it and, if it came from production, whether to treat its history as exposed
(deleting does not remove it from Git history; rewriting history or rotating
credentials is a separate decision). *.dump is now git-ignored so new dumps are not
committed, but the existing tracked file is untouched.
