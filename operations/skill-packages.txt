Agent Skill packages and validation
==================================

Authoring
---------
From the project root:
python backend/scripts/create_skill.py .check-results/my-alarm-skill --name alarm-summary
python backend/scripts/package_skill.py .check-results/my-alarm-skill .check-results/my-alarm-skill.zip

create_skill refuses to overwrite an existing directory. It creates SKILL.md,
scripts/summarize.py and runtime.json. This is a scaffold, not AI code generation.
Edit the implementation/instructions and increment metadata.version before
uploading a changed release. Existing manifest.json packages remain supported.

An Agent Skill ZIP may have a single enclosing directory. Its normalized root:
SKILL.md
runtime.json               optional explicit run specifications
scripts/summarize.py
references/data.csv        optional UTF-8 bundled data

SKILL.md example:
---
name: alarm-summary
description: Summarize supplied telecom alarm observations
metadata:
  version: "1.0.0"
---
Summarize supplied observations and state uncertainty. Do not claim live data.

Frontmatter supports name, description, license, compatibility, metadata and
allowed-tools. allowed-tools is descriptive metadata and never grants connector,
network, credential or shell capabilities. YAML duplicate keys, tags, anchors
and aliases are rejected. Names normalize to custom_alarm_summary; existing
name/version collisions are rejected, never overwritten. Instruction-only
packages are supported and do not start an executable sandbox.

Explicit runtime.json example:
{
  "scripts": [{
    "entrypoint": "scripts/summarize.py",
    "purpose": "Summarize supplied alarm text",
    "input_fields": [{"name":"text","kind":"string","required":true}],
    "sample_input": {"text":"Alarm at demo site"},
    "output_contract": "skill_result",
    "timeout_seconds": 10
  }]
}

The scripts array must cover every .py file under scripts/ exactly once.
Supported input kinds: string, integer, number, boolean, object and array, with
no extra fields. object/array inputs (for example a list of KPI records) declare
a "shape" and may be optional; an omitted optional array becomes [].
Example:
  {"name":"records","kind":"array","shape":{"type":"array","maxItems":500,
   "items":{"type":"object","required":["cell","drop_rate"],"properties":{
     "cell":{"type":"string","maxLength":20},
     "drop_rate":{"type":"number","minimum":0,"maximum":100}}}}}

Schema subset (services/skill_schema.py), shared by API arguments, review smoke
tests and runtime. Types: string (minLength/maxLength/enum), integer and number
(minimum/maximum/enum), boolean, array (items/minItems/maxItems) and object
(properties/required). Objects are always closed; additionalProperties may only
be false. Unknown keywords ($ref, oneOf, pattern ...) are rejected, not ignored.
Limits: depth 5, 200 schema nodes, 50 properties per object, 1000 items,
10000 characters per string, 50 enum values, 20000 value nodes, 256 KiB of
input JSON. NaN, Infinity and booleans used as numbers are rejected. Validation
errors name the field path and never echo submitted values.

Optional output_schema uses the same subset and validates the script's data:
"json" validates the whole JSON value, "skill_result" validates its data member
and "text" accepts only a string schema. Output that is valid JSON with the
wrong shape fails the smoke test and runtime call. The schema is part of the
reviewed run-spec hash, so changing it requires a new analysis and review;
reports for the old run-spec cannot approve it. Manifests without these fields
keep their previous hash, so existing approved versions and pending runs keep
working. Rollout needs no migration, but web and worker must run this version
before approving a package that uses object/array inputs or output_schema.
Each script receives its JSON arguments on stdin and as read-only /skill/args.json.
That filename is reserved and cannot be included in the uploaded package.
open('args.json') and literal read-only paths to bundled data are supported.

Output contracts:
- skill_result: JSON {"status":"success","data":{...}} (legacy default).
- json: any valid finite JSON value, wrapped as a successful SkillResult.
- text: UTF-8 stdout, wrapped as a successful SkillResult.
Exit failure, malformed/non-finite JSON, privileged approval requests or output
overflow fail validation. An exit-zero result does not override an invalid
contract. Every script must pass its own sample input in the real sandbox.

Imported package compatibility
------------------------------
Accepted entries: .py .json .md .txt .csv, .sh as an INERT text resource, and
YAML only as agents/<name>.yaml descriptive metadata (16 KB, no aliases/anchors/
tags/duplicate keys, must be a mapping). Any other file type, nested YAML or
binary is rejected. Shell files are stored and readable through read_skill_file
but are never executed: only declared Python entrypoints run in the sandbox, and
a .sh or .yaml file cannot be an entrypoint. Secret scanning covers all files.
The report gains a "compatibility" stage listing inert resources, metadata keys
and what the metadata does not grant. Metadata never gives tools, network,
connectors, credentials or approval. Import success is not run success: every
script still needs its smoke test and a different reviewer.

Checked against the reference project's packages (Agent_skill/*.zip):
ran-kpi-anomaly-triage and core-link-impact-summary now import (script plus
agents/openai.yaml; they have no runtime.json, so default run-spec is used and
real KPI inputs need a reviewed runtime.json). node-health-autoremediate,
unsafe-node-debug-shell, noc-alarm-enrichment and db-schema-discovery are still
rejected by static analysis (process, shell or database access); that is
intended, not a compatibility gap to close.

Reading instructions on demand
------------------------------
Tool descriptions in the catalog are short (description + purpose, at most 600
characters plus a pointer). The complete SKILL.md and bundled files are read by
the agent through two read-only tools registered for every run:
- load_skill(skill_name, offset, limit): SKILL.md in chunks of at most 12000
  characters and 8 KB encoded (below the 16 KiB tool output limit, so nothing is
  withheld), with next_offset and the list of bundled files (first 60 paths).
- read_skill_file(skill_name, path, offset, limit): one bundled text file, by
  exact path from that list. Paths are dictionary keys of the reviewed archive;
  nothing is resolved on a filesystem, so ../, absolute paths and unlisted names
  fail.
Both read the version PINNED by the run, never the newly active one, and refuse
a revoked or changed version. Content is returned with a notice that it is
untrusted reference text: it cannot change policy, grant approval, widen scope
or authorize an action. They are allowed for site-restricted principals because
they expose reviewed package text, never alarm, inventory or host data.

Choosing a specific skill
-------------------------
POST /api/runs accepts optional "skill" (omitted or null = auto, all pinned
skills). The server accepts only built-in names or approved and currently active
packages (HTTP 422 otherwise) and stores it in runs.requested_skill (migration
0011). A specific run exposes only that package's tools plus the two readers,
and the engine refuses every other tool until load_skill for that package has
returned in THIS run (an earlier run's load does not count; survives approval
resume because it is derived from the saved messages). The skill is part of the
idempotency hash only when set, so auto-mode retries behave as before. If the
package is revoked before execution, the run fails instead of using another one.
Run snapshots report "skill": "auto" or the selected name.

Multiple scripts become separate tools with stable path-derived suffixes.
Runs pin both package content and resolved run-spec hashes. Updating the active
version does not change a waiting run. Revoking a version blocks future calls.

Validation and review
---------------------
1. Inspect: parse/archive limits, secret scan and detailed AST file/line findings.
2. Upload: quarantine the immutable archive, manifest and initial report.
3. Validate: telecom taxonomy, optional LLM domain review/run-spec suggestions,
   then sandbox smoke testing of every declared script.
4. A different reviewer inspects source, schemas, sample inputs and report,
   submits notes and approves/rejects against the current report hash.
5. Admin activates the approved version; revoke removes its active selection.

Offline validation never calls an LLM. The UI opt-in explicitly authorizes
sending source to one selected provider and may incur charges. Chat fallback
providers are disabled for skill review. Existing model timeout, retry, context
and cost-admission limits also apply to this call. No provider price is hardcoded.

The LLM result must match a typed schema and reference only bundled script paths.
It never approves a skill. Author-supplied runtime.json contracts remain
authoritative; suggestions are shown for review. For packages without explicit
contracts, valid suggestions can become the effective draft specifications,
which must still pass sandbox testing and be reviewed by a different person.
A taxonomy match (score >= 0.25) or valid LLM domain score >= 0.5 is required.
Scores indicate domain relevance; they do not establish code safety.

Reports include policy version, archive/run-spec hashes, each script's schema,
bounded smoke output, errors and human decision. Failed smoke reports are saved
while the artifact remains quarantined. Review repeats smoke tests. Concurrent
re-analysis/revoke invalidates an in-flight stale decision instead of reviving
the artifact. After a failed review, inspect the latest report before retrying.

API (bearer authentication and skill_reviewer/admin roles apply):
POST /api/skills/inspect       raw ZIP body; does not persist or execute code
POST /api/skills               raw ZIP body; creates a quarantined version
POST /api/skills/{id}/analyze  {content_hash,use_llm:false,provider:"openai"}
POST /api/skills/{id}/review   {content_hash,report_hash,approved,notes}
POST /api/skills/{id}/activate admin only
POST /api/skills/{id}/revoke   admin only

Limits and deployment
---------------------
ZIP <= 2 MiB, expanded <= 8 MiB, <= 100 files, <= 20 declared scripts.
Python source <= 128 KiB/file and <= 20,000 AST nodes. Only supported
transformation imports, standard input/output streams and literal workspace
file reads are allowed by static policy. Reflection/dunder/process/environment
access, syntax errors and likely secrets produce findings. AST is a screening
aid and is not a proof that arbitrary Python is safe.

Docker remains the execution boundary: non-root, read-only filesystem/code and
arguments, network none, no host credentials/socket, resource/output/deadline
limits. Configure a dedicated broker daemon and a reviewed pre-pulled SANDBOX_IMAGE
digest as described in runbook.txt. Missing sandbox never uses host Python.
The whole validation pass defaults to 120 seconds (SKILL_VALIDATION_TIMEOUT_SECONDS),
with at most two simultaneous validations per web process. Each script has a
1-30 second runtime limit. No automatic package installation or connector access.

Release migration 0009 adds nullable skill_versions.validation_report and
preserves old archives. Production startup still requires an explicit migration
release job. New activation requires the current report and human approval;
an older approved artifact without that evidence needs a reviewed new version.
Fixture mode supports offline validation; paid review is rejected in fixture mode.

Site capabilities and the data broker (P1-07)
---------------------------------------------
Built-in tools site_inventory(site, limit) and site_alarm_overview(site, limit)
(services/site_capabilities.py). A site is an exact station id or an exact,
case-insensitive station name (never a pattern). Order of operations: resolve
the station, authorize the principal for it, and only then query devices and
alarms. Queries are fixed backend templates: parameterized, read-only
(inventory sessions are default_transaction_read_only with a 10 s statement
timeout; alarm queries use max_execution_time 10 and LIMIT), at most 500
devices and 100 alarms per call, with truncation flags. The ClickHouse/Postgres
accounts should themselves be read-only.

Row scope: auth principals accept an optional "sites" list (station ids or
names, case-insensitive, "*" for all); admins see all. A principal without
sites sees none. Restricted principals still cannot call the aggregate tools
(alarm_statistics etc.); the two site tools are the scoped way in.

Results that are different on purpose: SITE_NOT_FOUND, SITE_AMBIGUOUS (lists
only sites the caller may see), SITE_FORBIDDEN (business errors),
CONNECTOR_UNAVAILABLE (system error, no data), and success with data_status
ok / no_devices / no_active_alarms. Every success carries provenance (sources,
queried_at, observed_at null: retrieval time is not freshness).

Brokered data for reviewed scripts: a run-spec may declare
  "capability": "site_inventory" | "site_alarms", "capability_field": "<array input>"
with a required string input "site" and a required array input named by
capability_field (with a shape, e.g. maxItems 200) plus a sample_input holding
sample records for the smoke test. The agent supplies only "site"; at runtime
the backend authorizes the site, fetches records (limited to the field's
maxItems), re-validates the whole input with the reviewed schema and passes it
to the sandbox as JSON. The script never gets DSNs, passwords, SQL, SSH or
network. capability/capability_field are part of the reviewed run-spec hash and
the report, an LLM review cannot propose them, and scripts without them receive
no data. A brokered skill is allowed for site-restricted principals because the
broker enforces row scope; the data it returns is limited to their sites.

Rollout: new built-in names change the pinned built-in catalog, so finish or
cancel queued/waiting runs before deploying (as for migration 0010); old runs
fail with "Built-in catalog changed" instead of silently gaining tools.
